# YourTal — Patterns From The Giants

**Date:** 2026-09-18
**Why this doc exists:** nothing here is novel. Every subsystem we need has been built, at scale, by a company that published how. This is the borrow list: **who to copy, the exact pattern to take, what they got wrong, and where we differ on purpose.**

Rule for using this doc: **copy the mechanism, not the org chart.** These patterns were built by hundreds of engineers for a hundred times our load. Take the shape, ship the smallest correct version.

---

## 1. API design — copy **Stripe**

Our merchant Redemption API ([`09`](09-points-economy-and-redemption.md) §10) is the surface a partner's checkout engineer meets at 2 a.m. It is the product.

| Concern         | What Stripe does                                                                                                                                                                                                                                                                                                                                                                                                                 | What we adopt                                                                                                                                                                                                                                                                                            |
| --------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Versioning**  | Named major releases (Acacia, Basil…) contain breaking changes; monthly releases are backward-compatible only. Version pinned per account, overridden per request with `Stripe-Version`; **webhook endpoints pin their own version**; 72h rollback window ([upgrades](https://docs.stripe.com/upgrades), [versioning](https://docs.stripe.com/api/versioning))                                                                   | Same model. Publish the backward-compatible list verbatim: new resources, new optional params, new response properties, new event types — **clients must tolerate unknown fields and unknown event types**                                                                                               |
| **Idempotency** | `Idempotency-Key` on POST only, ≤255 chars, UUIDv4 suggested. Status + body of the first request are cached **including 500s**; replaying a key with different params returns `idempotency_error` / `409`; keys pruned after ≥24h; requests that failed validation or raced are _not_ saved and are safe to retry ([idempotent requests](https://docs.stripe.com/api/idempotent_requests))                                       | Identical semantics, but keys retained **for the voucher's life + 30d** (Amazon's rule: resource lifetime plus a late-arrival interval — [AWS Builders' Library](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)). Store the request-param hash and reject mismatches |
| **Errors**      | `400/401/402/403/404/409/424/429/5xx`; four `type`s (`api_error`, `card_error`, `idempotency_error`, `invalid_request_error`); object carries `code`, `param`, `message`, `doc_url`, `request_log_url` ([errors](https://docs.stripe.com/api/errors))                                                                                                                                                                            | Same envelope. `doc_url` and `request_log_url` on **every** error — a merchant dev should never have to open a support ticket to learn what a code means                                                                                                                                                 |
| **Pagination**  | Cursor-only: `starting_after` / `ending_before` take an **object ID**, `limit` 1–100 (default 10), envelope `{object:"list", data, has_more, url}` ([pagination](https://docs.stripe.com/api/pagination))                                                                                                                                                                                                                        | Same. No offset pagination anywhere, ever — it double-counts under concurrent writes, which for a ledger is a correctness bug, not a UX one                                                                                                                                                              |
| **Expansion**   | `expand[]` on any endpoint, dotted nesting, `data.` prefix inside lists, **max depth 4** ([expanding](https://docs.stripe.com/api/expanding_objects))                                                                                                                                                                                                                                                                            | Same, capped at **depth 2**. Merchants need `voucher.campaign`, not a graph traversal                                                                                                                                                                                                                    |
| **Webhooks**    | `Stripe-Signature: t=…,v1=…`; signed payload is `timestamp + "." + raw body`, HMAC-SHA256 with the endpoint secret, **5-minute default tolerance**, constant-time compare, multiple active secrets for ≤24h during rotation. Retries with exponential backoff **for up to 3 days**; return `2xx` before doing work; **no ordering guarantee** — dedupe on event ID, not `created` ([webhooks](https://docs.stripe.com/webhooks)) | All of it, including IP allowlist + signature as belt and braces, and secret rotation with an overlap window                                                                                                                                                                                             |

**What they do badly → our improvement.** Stripe pushes two hard problems onto the integrator: (a) _no ordering guarantee_ and (b) _webhooks or nothing_. A convenience-store POS vendor will get both wrong.

- Every voucher event carries a **monotonic `sequence` per voucher**; a lower sequence than the merchant has already applied is safely ignorable, and we say so in the docs.
- **Webhook and poll parity:** `GET /v1/events?after=<event_id>` replays the exact same event stream. A merchant who cannot host a public HTTPS endpoint is still a first-class integrator.
- Error `code` carries an explicit **`retryable: true|false`** plus `voucher_state`. No merchant should be inferring retry-safety from a string.

**Our differentiator:** the redemption endpoints are **two-phase by default** (`authorize` → `capture`, with `void` on timeout), so a failed merchant checkout can never strand a user's voucher — the card-network shape from [`09`](09-points-economy-and-redemption.md) §10, exposed with Stripe's ergonomics.

## 2. Money and the ledger — copy **Square, Uber, Airbnb, Stripe**

| Concern                        | What they do                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             | What we adopt                                                                                                                                                                                                                                                                                                                      |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Double-entry, enforced**     | Square's Books service is three tables — `books`, `journal_entries`, `book_entries` — and **every journal entry must balance to 0**, so that "$100 of paid-out ledger entries but $50 of payouts" is impossible ([Square Eng](https://developer.squareup.com/blog/books-an-immutable-double-entry-accounting-database-service/)). Uber: "all entries in any money order sum to zero… no money can ever be created or destroyed" ([Uber Eng](https://www.uber.com/us/en/blog/ubers-payments-platform/))                                                                                                                   | The same three-table shape for the points ledger and the cash ledger. The balance-to-zero check is a **database constraint**, not a service-layer assertion                                                                                                                                                                        |
| **Immutability + corrections** | Square: "there are no update statements… only inserts"; a mistake is fixed by "a new entry that corrects the previous one" ([Square Eng](https://developer.squareup.com/blog/books-an-immutable-double-entry-accounting-database-service/)). Uber: "an order once written can't be changed in any shape or form", adjustments are supplementary orders ([Uber Eng](https://www.uber.com/us/en/blog/ubers-payments-platform/)), and LedgerStore records are "verifiably immutable… using cryptographic signatures" ([Uber Eng](https://www.uber.com/us/en/blog/migrating-from-dynamodb-to-ledgerstore/))                  | Append-only, no `UPDATE`, no `DELETE`, revoked permissions to prove it. A clawback is a reversing entry with a reason code                                                                                                                                                                                                         |
| **Concurrency**                | Square keeps "a monotonic counter for each book reflecting its current version" ([Square Eng](https://developer.squareup.com/blog/books-an-immutable-double-entry-accounting-database-service/))                                                                                                                                                                                                                                                                                                                                                                                                                         | Per-account version for optimistic concurrency; a stale write loses and retries                                                                                                                                                                                                                                                    |
| **Idempotent money movement**  | Airbnb's Orpheus splits every payment request into **Pre-RPC (record intent) → RPC (network only, no DB writes) → Post-RPC (record result)**, each phase its own atomic transaction, sharded by idempotency key, with client retries using exponential backoff and jitter ([Airbnb Eng](https://medium.com/airbnb-engineering/avoiding-double-payments-in-a-distributed-payments-system-2981f6b070bb))                                                                                                                                                                                                                   | The exact three-phase shape for settlement payouts and for redemption capture. Never hold a DB transaction open across a network call to a merchant                                                                                                                                                                                |
| **Minor units, never floats**  | Stripe takes all amounts as **integers in the currency's minor unit** — `1099` = 10.99 USD, `10` = 10 JPY — and documents the traps: ISK/UGX are zero-decimal but must still be sent ×100, HUF/TWD are zero-decimal for payouts only, and **IDR is a two-decimal currency at Stripe** ([currencies](https://docs.stripe.com/currencies)). Binary floats can't represent 0.1 exactly, which is why decimal types are "preferred in accounting applications which have strict equality invariants" ([Python docs](https://docs.python.org/3/library/decimal.html))                                                         | One `Money` type = `(int64 amount_minor, currency)` — Fowler's Money pattern of amount-plus-currency in a single type ([Fowler](https://martinfowler.com/eaaCatalog/money.html)). **Store IDR in sen (×100)** even though nobody quotes sen, because our processors will. Points are plain integers with no fractional unit — ever |
| **Reconciliation**             | Uber matches its ledger to 50+ PSPs using "a deterministic field called `transactionReference`" established at payment time; unmatched records go to a DLQ and are retried; ~1.2B settlements/month, reconciliation landing about T+7 ([Uber Eng](https://www.uber.com/en-CH/blog/ubers-advanced-settlement-accounting-system/)). Their Finance Computation Platform "guarantees to always produce the same transaction for a given event" and runs "multiple batch-based reconciliations… set comparisons across systems and sources" ([Uber Eng](https://www.uber.com/us/en/blog/ubers-finance-computation-platform/)) | A deterministic reference minted at the moment of the event and carried to the PSP, the merchant and the ledger. Nightly three-way set comparison: **our ledger ↔ PSP ↔ merchant settlement statement**, with an exceptions queue a human owns                                                                                     |

**What they do badly → our improvement.** Square's `books` table is explicitly "inherently mutable (current balance is updated on every operation)" — a sane concession at millions of payments a day that we do not need at [`10`](10-tech-stack.md)'s load. We keep the balance as a **projection**, and a nightly job re-derives every balance from the entries and alerts on any divergence. If our cached balance ever disagrees with the entries, we find out that night, not at audit.

**Our differentiator:** **the solvency invariant is a ledger query, not a report.** The coverage ratio from [`09`](09-points-economy-and-redemption.md) §5 is computed from the same entries, on the same schema, and the "no unfunded faucet" rule is enforced as a double-entry constraint — a promotional point grant whose matching cash leg from the marketing account is missing **fails the transaction**. You cannot mint an unbacked point through the API, because the API cannot write an unbalanced entry.

## 3. Video upload + moderation at scale — copy **YouTube, TikTok** (UGC) and **Meta/Google Ads** (creative review)

**Read this first: we are an ad platform, not a UGC platform.** YouTube and TikTok moderate **after** publication because they must — a billion uploads cannot wait. Meta and Google Ads review **before** a single impression, because an ad is a paid, bounded, commercial object. Business campaign videos are ads. **We gate on upload. Copy the ad-review model for the pipeline and the UGC model for the tooling.**

| Concern                               | What they do                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        | What we adopt                                                                                                                                                                                                                               |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Pre-publication gate + SLA**        | Meta: "Our ad review process starts automatically before ads begin running, and is typically completed within 24 hours"; review covers images, video, text, targeting **and the landing page** ([Meta ad standards](https://transparency.meta.com/policies/ad-standards/)). Google: "Most ads are reviewed within one business day", covering "headline, description, keywords, destination, and any images and video" ([Google Ads](https://support.google.com/adspolicy/answer/1722120?hl=en))                                                                                                                                                                    | A published **24-hour review SLA** on the advertiser console, shown as a countdown. Review covers the video, the **quiz questions**, the voucher offer and the destination URL — the question set is ad copy and can mislead just as easily |
| **Automated first, human for nuance** | Meta: "Our ad review system relies primarily on automated tools" ([ibid.](https://transparency.meta.com/policies/ad-standards/)). Google: violating content "is either removed by Google's AI or, where a more nuanced determination is required, it is flagged for further review by trained operators", and those manual decisions become training data ([Google](https://support.google.com/adspolicy/answer/13584894?hl=en)). YouTube: "AI classifiers help detect potentially violative content at scale, and reviewers work to confirm whether content has actually crossed policy lines" ([YouTube](https://www.youtube.com/intl/en_us/howyoutubeworks/ai/)) | Classifier → **auto-approve only the confidently clean**; everything else to a human queue. **Log every human decision as labelled training data from day one** — at our volume the reviewer _is_ the dataset                               |
| **Edits re-enter review**             | Meta: edited or fixed ads "will be treated as new ads and reviewed by our ad review system", and "ads remain subject to review and re-review at all times" ([ibid.](https://transparency.meta.com/policies/ad-standards/)). Google: "Changes to your ad or assets restart the review process" ([Google](https://support.google.com/adspolicy/answer/1722120?hl=en))                                                                                                                                                                                                                                                                                                 | Any change to video, questions or offer resets to `in_review`. Approval is bound to a **content hash**, so a swapped file cannot inherit an approval                                                                                        |
| **Hash matching for known-bad**       | YouTube auto-scans every upload against a reference database via Content ID and applies block/monetize/track ([Content ID](https://support.google.com/youtube/answer/2797370?hl=en))                                                                                                                                                                                                                                                                                                                                                                                                                                                                                | Perceptual hash of every uploaded video against (a) previously rejected creatives and (b) our own approved library. Re-uploading a rejected video should be rejected in milliseconds, free                                                  |
| **Graduated account enforcement**     | YouTube: first violation is a **warning only**, expiring after 90 days; then 1-week, 2-week blocks, and 3 strikes in a 90-day window can remove the channel ([strikes](https://support.google.com/youtube/answer/2802032?hl=en)). Google Ads runs a parallel **account-level** three-strike system — warning first, then 3-day hold, 7-day hold, then suspension — across 15 named policies ([three strikes](https://support.google.com/adspolicy/answer/10922738?hl=en))                                                                                                                                                                                           | Two separate enforcement objects: **creative rejection** (cheap, routine, no stigma) and **advertiser account strikes** (warning → funding hold → suspension). Conflating them punishes a careless marketer like a fraudster                |
| **Appeals with a clock**              | YouTube: strikes appealable within 6 months, removals within a year, one appeal each, outcome = reinstate / age-restrict / uphold ([appeals](https://support.google.com/youtube/answer/185111?hl=en)). Meta advertisers request review in Account Quality ([ibid.](https://transparency.meta.com/policies/ad-standards/))                                                                                                                                                                                                                                                                                                                                           | One appeal per decision, human-reviewed, with an SLA. Rejection reasons cite **the specific policy clause**, not a category                                                                                                                 |
| **Policy taxonomy**                   | Google's strike system enumerates 15 concrete policies by name ([ibid.](https://support.google.com/adspolicy/answer/10922738?hl=en))                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                | A short, numbered, public policy list from day one — versioned, dated, and linked from every rejection. Write it before the first upload, not after the first argument                                                                      |

**What they do badly → our improvement.** Both models leak in opposite directions. UGC platforms accept enormous absolute error volumes as the price of scale — YouTube reports automated flagging catching **94% of violative content**, with **75% removed before 10 views**, and a violative view rate around **0.16–0.18%** ([YouTube blog](https://blog.youtube/inside-youtube/building-greater-transparency-and-accountability/)); TikTok similarly reports **over 80% of removals** by automation and says it removes "1% or less of published content" ([TikTok newsroom](https://newsroom.tiktok.com/en-us/bringing-even-more-transparency), [enforcement](https://newsroom.tiktok.com/en-us/evolving-our-approach-to-content-enforcement-us)). Excellent ratios — and still millions of mistakes. Ad platforms err the other way: opaque rejections with generic reasons and no way for the advertiser to see what tripped.

We have **hundreds of creatives, not millions** ([`10`](10-tech-stack.md) §0). That makes a luxury affordable that neither can afford: **every single campaign video gets human eyes before it earns a point.** The classifier exists to sort and pre-annotate the queue, never to auto-reject.

**Our differentiator:** the reward mechanic gives us a moderation signal nobody else has — **the quiz**. A creative whose questions are unanswerable, whose completion rate collapses, or whose viewers systematically fail is either misleading or worthless, and it is auto-flagged for re-review _after_ approval on live performance data. We also review a dimension the giants don't have: **the offer** — a voucher that can't actually be redeemed is the worst policy violation on our platform, and it is invisible to any classifier trained on video.

## 4. Catalogue and commerce — copy **Shopify** (modelling) and **Amazon** (idempotent order flow)

| Concern                 | What they do                                                                                                                                                                                                                                                                                                                                                                                                                                  | What we adopt                                                                                                                                                                                                            |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Product modelling**   | Shopify: `Product` → `options` (size, colour) → `variants` = option combinations; **SKU and inventory item live on the variant**, not the product; up to 2048 variants per product ([Product object](https://shopify.dev/docs/api/admin-graphql/latest/objects/Product))                                                                                                                                                                      | Store item = `product` + `variant`; a voucher denomination (IDR 25k / 50k / 100k) is a **variant**, not three products. Points price attaches to the variant                                                             |
| **Inventory states**    | Shopify splits stock into `on hand` = `available` + `committed` + `reserved` + `damaged` + `safety stock` + `quality control`, plus `incoming`. Placing an order moves units **available → committed**; fulfilment decrements committed ([inventory states](https://shopify.dev/docs/apps/build/orders-fulfillment/inventory-management-apps))                                                                                                | The same state split for supplier inventory, with `safety stock` used exactly as intended — a buffer that prevents overselling a partner's vouchers                                                                      |
| **Idempotent checkout** | Amazon: a caller-supplied **client request identifier** recorded _in the same atomic transaction_ as the mutation; original parameters stored alongside it; a retry with the same token but different params returns a **parameter-mismatch validation error**; retries get a **semantically equivalent response**, not an error ([AWS Builders' Library](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)) | Checkout is one `POST /orders` with an idempotency key; the points debit and the stock commit happen in one Postgres transaction with the key. A double-tapped "Redeem" button is physically incapable of spending twice |
| **Order state machine** | Explicit states with compensating transitions (auth/capture/void is the same idea from the card networks — see [`09`](09-points-economy-and-redemption.md) §10)                                                                                                                                                                                                                                                                               | `held → paid → issued → fulfilled → settled`, plus `expired` and `refunded`. Every transition is a ledger entry; no state is inferred from the absence of another                                                        |

**What they do badly → our improvement.** Shopify only commits stock when the **order is placed** — the cart window is unprotected, which is why Shopify merchants oversell during drops. We cannot afford that: our user has just spent 20 minutes earning the points and a sell-out at checkout is the worst moment in the product.

**Our differentiator:** one object, the **`Hold`**, reserves _stock and the points price together_ with a single expiry that matches the 10–15 minute price lock from [`09`](09-points-economy-and-redemption.md) §4.2. Price lock and stock lock cannot drift apart because they are the same row. Expiry releases both.

## 5. Auth and identity as a provider — copy **Google**

YourtalID is an OIDC provider for the sister apps ([`02`](02-architecture.md) §2). The bar is "feels as safe as Sign in with Google".

| Concern                    | What Google / the spec does                                                                                                                                                                                                                                                                                                                                                               | What we adopt                                                                                                                                                            |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Consent & scope design** | Google shows a **granular permissions screen**: users tick scopes individually, so apps **must check which scopes were actually granted** and degrade features accordingly. Official guidance is to request **one scope at a time, in context**, not a bundle at sign-in ([granular permissions](https://developers.google.com/identity/protocols/oauth2/resources/granular-permissions)) | Partial grants are a supported state, enforced server-side. Sign-in asks for identity only; `points.read` when a balance is first shown; `points.spend` only at checkout |
| **Incremental auth**       | `include_granted_scopes=true` merges a new grant with previously granted scopes ([OIDC](https://developers.google.com/identity/protocols/oauth2/openid-connect))                                                                                                                                                                                                                          | Same parameter, same semantics — a sister app never has to re-ask for what it already holds                                                                              |
| **Replay / CSRF**          | `state` for CSRF, `nonce` for replay; ID tokens validated on five checks: signature, `iss`, `aud`, `exp`, and `hd` where applicable ([OIDC](https://developers.google.com/identity/protocols/oauth2/openid-connect))                                                                                                                                                                      | Verbatim. The five checks are a test case, not a code comment                                                                                                            |
| **Token hygiene**          | [RFC 9700](https://datatracker.ietf.org/doc/html/rfc9700) (OAuth 2.0 Security BCP): public clients **MUST** use PKCE and AS **MUST** support it; refresh tokens for public clients **MUST** be sender-constrained **or rotated**; redirect URIs matched by **exact string** (no patterns); implicit grant SHOULD NOT be used                                                              | All four, day one. Rotation with **replay detection**: a reused refresh token revokes the entire token family and logs a security event                                  |

**What they do badly → our improvement.** Google's consent screen names API scopes, not consequences — "See and download your contacts" is as far as it goes, and the developer verification path is famously slow and opaque. Our scopes touch **money**, so the screen states the consequence and the limit in the user's language: _"Kopi Kenangan app can spend up to 5,000 points per purchase on your behalf."_ Plus a self-serve **connections dashboard** listing what each app actually accessed, with one-click revoke.

**Our differentiator:** **value-bearing scopes carry a cap.** `points.spend` is never granted unbounded — it is granted with a per-transaction limit, and exceeding it forces step-up re-consent. Scope plus limit, not scope alone.

## 6. Anti-abuse — copy **Cloudflare, Google, Meta**

| Concern                       | What they do                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   | What we adopt                                                                                                                                                             |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Score, don't verdict**      | Cloudflare emits a **bot score 1–99** (1 = certainly automated, 30–99 = likely human) rather than a boolean ([Cloudflare](https://developers.cloudflare.com/bots/concepts/bot-score/)). reCAPTCHA returns **0.0–1.0** with a suggested starting threshold of 0.5 ([reCAPTCHA v3](https://developers.google.com/recaptcha/docs/v3))                                                                                                                                                                                                                                                                                                                                                             | One risk score per watch session, per quiz submission and per redemption. Thresholds are config, tuned per market — ID and AU will not share a number                     |
| **Graduated response**        | Google is explicit: "we recommend that you take the action in the background instead of blocking traffic", e.g. "with low scores, require MFA or email verification", or "send risky comments to moderation" ([reCAPTCHA Enterprise](https://docs.cloud.google.com/recaptcha/docs/interpret-assessment-website)); tiered guidance puts MFA in the 0.0–0.5 band and free passage above it ([best practices](https://docs.cloud.google.com/recaptcha/docs/best-practices-oat)). Cloudflare's `managed_challenge` "dynamically choose[s] the appropriate type of challenge" instead of a flat `block` ([rules actions](https://developers.cloudflare.com/ruleset-engine/rules-language/actions/)) | A five-rung ladder: **allow → escrow the points → challenge (Turnstile) → step-up verify (phone) → block**. Blocking is the last rung, not the first                      |
| **Observe before enforcing**  | Cloudflare's `log` action is "recommended for validating rules before applying more severe actions" ([ibid.](https://developers.cloudflare.com/ruleset-engine/rules-language/actions/)); Google says to use the analytics dashboard to pick thresholds before acting on them ([best practices](https://docs.cloud.google.com/recaptcha/docs/best-practices-oat))                                                                                                                                                                                                                                                                                                                               | **Every new rule ships in log-only mode** and must show a week of clean data before it can deduct a single point                                                          |
| **Invisible friction**        | Turnstile replaces puzzles with browser signals and lightweight proof-of-work — "Cloudflare will never issue another visual puzzle to anyone, for any reason" — and states it doesn't rely on tracking user data ([Cloudflare blog](https://blog.cloudflare.com/turnstile-ga/))                                                                                                                                                                                                                                                                                                                                                                                                                | Turnstile over any CAPTCHA. Our users are on mid-range Android over patchy mobile data; a puzzle at the end of a 20-minute video is a churn event                         |
| **Reduce, don't only remove** | Meta's strategy is **remove / reduce / inform** — content that doesn't violate policy but is low-quality gets reduced distribution rather than deletion ([about.fb.com](https://about.fb.com/news/2019/04/remove-reduce-inform-new-steps/), [transparency.meta.com](https://transparency.meta.com/enforcement/taking-action/lowering-distribution-of-problematic-content/))                                                                                                                                                                                                                                                                                                                    | The shadow tier is **demotion and escrow, not silent deletion**: a suspected farm account still watches, still accrues, and simply cannot cash out until it clears review |
| **Signals at registration**   | Meta "block[s] millions of attempts to create fake accounts every day and detect[s] millions more, often within minutes after creation", looking for "signals that indicate if accounts are created in mass from one location" ([fake accounts](https://about.fb.com/news/2019/05/fake-accounts/))                                                                                                                                                                                                                                                                                                                                                                                             | Registration-time clustering on device, network and behaviour — the cheapest point in the funnel to stop a farm is before it earns anything                               |
| **Positive signals too**      | reCAPTCHA Account Defender builds "a site-specific model… to detect a trend of suspicious behavior", and lets you mark devices trusted to "reduce friction for users logging in from one of their trusted devices" ([Account Defender](https://docs.cloud.google.com/recaptcha/docs/account-defender))                                                                                                                                                                                                                                                                                                                                                                                         | Trust accrues: a user with 90 days of clean redemptions skips challenges that a day-old account gets                                                                      |

**What they do badly → our improvement.** The giants are honest that they get this wrong a lot — Meta stated that as of December 2024 "one to two out of every 10" enforcement actions "may have been mistakes" ([Meta integrity report](https://transparency.meta.com/reports/integrity-reports-q1-2025/)) — and their appeals are slow, opaque and largely unexplained. At their scale that is survivable. At ours, wrongly voiding the points a real user earned over a fortnight is an unrecoverable churn event and a screenshot on Indonesian Twitter.

So: **false positives must be cheap and fast to reverse by construction.** Points are never destroyed on suspicion, only **held**, with a reason code, a visible countdown, a one-tap appeal, and **automatic release if review doesn't happen inside the window**. Meta's own practice supports the auto-restore half of this — they restore content they later find was wrongly removed even without an appeal, and restore duplicates in bulk when one person appeals ([restored-content metric](https://transparency.meta.com/policies/improving/restored-content-metric/)) — so when a rule is found faulty we release **every** hold that rule created, not just the ones that complained.

**Our differentiator:** **escrow instead of ban.** Hard blocks are reserved for confirmed farms (shared device fingerprint, shared payout instrument, impossible watch velocity). Everything softer becomes a hold on _value_, not a lock on the _account_ — and we never show the user the score or the rule that caught them, per Google's advice not to tip off attackers ([best practices](https://docs.cloud.google.com/recaptcha/docs/best-practices-oat)).

## 7. Feature flags and experimentation — copy **Netflix, Booking.com, Meta**

**Why this is a value-path subsystem, not a nice-to-have.** Every parameter in [`09`](09-points-economy-and-redemption.md) — backing rate `B`, the demand multiplier, faucet sizes, quiz thresholds — is a guess until it is measured. And a bad guess on an economy parameter does not degrade the product, it **transfers money**. The flag system is how we change those numbers without betting the reserve.

| Concern                           | What they do                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         | What we adopt                                                                                                                                                                                                          |
| --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Flag ≠ deploy**                 | Meta ships behind Gatekeeper so code release is decoupled from feature release: "If we do find a problem, we can simply switch the gatekeeper off rather than revert back to a previous version or fix forward", ramping employees → **2% of production** → 100%, with push-blocking alerts and "an emergency stop button" ([Meta Eng](https://engineering.fb.com/2017/08/31/web/rapid-release-at-massive-scale/))                                                                                                                                                                                                                                                                                                                                                                                                                                   | Every economy parameter is a flagged value with an **owner, a default and a kill switch**. No economy change ever requires a deploy to undo                                                                            |
| **Ramp, don't launch**            | Kohavi's guidance: run 50/50 for maximum power, but only _after_ a ramp at smaller percentages to catch egregious errors ([ML encyclopedia entry](https://exp-platform.com/Documents/2023-03-11EncyclopeiaMLDSABTestingFinal.pdf)); "an experiment generally starts by directing a small percentage of users to the treatment… [and] gradually increases" ([ICSE 2017](https://exp-platform.com/Documents/2017-05%20ICSE2017_CharacterizingExP.pdf))                                                                                                                                                                                                                                                                                                                                                                                                 | 1% → 5% → 50/50 for anything touching issuance or pricing. The 1% stage exists to catch a decimal-point error, not to measure anything                                                                                 |
| **Guardrails with auto-shutdown** | Guardrails are "the sentinel to the health of the product. If metrics in this group change drastically… ExP informs an alert system, which shuts the experiment automatically down and all traffic will be sent to the prior version" ([ICSE 2017](https://exp-platform.com/Documents/2017-05%20ICSE2017_CharacterizingExP.pdf)); Microsoft defines them as metrics "we don't want to degrade but won't necessarily improve", with alerts on movement and/or p-value ([Microsoft ExP](https://www.microsoft.com/en-us/research/group/experimentation-platform-exp/articles/patterns-of-trustworthy-experimentation-during-experiment-stage/)). Booking uses the control group as "a safety net… all the traffic can be directed to the control group while studying the issue" ([Booking, KDD 2019](https://dl.acm.org/doi/10.1145/3292500.3330744)) | **Mandatory guardrails on every economy experiment: points issued per DAU, cost per completed watch, coverage ratio, redemption margin, settlement lag.** Breach → automatic revert to control, page the economy owner |
| **Pick the OEC carefully**        | Kohavi: the OEC is a single short-horizon metric predictive of long-term goals, and **"Profit" is explicitly a bad OEC** because short-term moves like raising prices inflate it ([ibid.](https://exp-platform.com/Documents/2023-03-11EncyclopeiaMLDSABTestingFinal.pdf))                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           | Our OEC is **retained watch-and-redeem behaviour**, never platform margin. Margin is a guardrail. Cutting rewards always "wins" on margin this week and empties the app by quarter-end                                 |
| **Long-term holdout**             | Uber's XP supports a **"universal holdout… used to measure the long-term effects of all experiments for a specific domain"** ([Uber Eng](https://www.uber.com/en-IN/blog/xp/)); Netflix runs long-running holdbacks for the same reason ([Netflix XP paper](https://ar5iv.arxiv.org/html/1910.03878))                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                | A permanent **1% universal holdout on the points economy**. It is the only way to see inflation, novelty decay and cumulative reward fatigue, none of which show up in a two-week read                                 |
| **Trigger the analysis**          | Booking: analyse only the users the treatment actually affected — untriggered users "dilute" the effect, cut power and inflate false discovery; their C/T1/T2 design separates the value of a model from the cost of the machinery that runs it ([KDD 2019](https://dl.acm.org/doi/10.1145/3292500.3330744))                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         | Price-multiplier tests are analysed only over users who **saw a different price**. Otherwise the effect drowns in users who never opened the store                                                                     |
| **Stop early when it's bad**      | Netflix's design-based confidence sequences allow continuous peeking; they report a method that "would have stopped a 30,000 person Netflix experiment after the first 100 people" ([Netflix, arXiv 2210.08639](https://arxiv.org/abs/2210.08639)). Uber pairs sequential testing with automated pausing on significant degradation ([Uber Eng](https://www.uber.com/en-IN/blog/xp/))                                                                                                                                                                                                                                                                                                                                                                                                                                                                | Sequential tests on the guardrails only. We peek for harm continuously; we do **not** peek for wins                                                                                                                    |
| **Expect to lose**                | Of 21,220 Bing experiments, only **33.4%** shipped to all users ([ICSE 2017](https://exp-platform.com/Documents/2017-05%20ICSE2017_CharacterizingExP.pdf)); Kohavi reports ~10% at Google and that "Netflix considers 90% of what they try to be wrong" ([ibid.](https://exp-platform.com/Documents/2023-03-11EncyclopeiaMLDSABTestingFinal.pdf)). Booking found offline model gains correlate essentially **not at all** with business value (Pearson r ≈ −0.1 across 23 comparisons) ([KDD 2019](https://dl.acm.org/doi/10.1145/3292500.3330744))                                                                                                                                                                                                                                                                                                  | Plan the roadmap for a ~1-in-3 hit rate, and **never ship a ranking or pricing model on offline metrics alone**                                                                                                        |

**What they do badly → our improvement.** These platforms are built for tens of thousands of tests a year (Booking is reported at ~25,000 annually — [HBR](https://hbr.org/2020/03/building-a-culture-of-experimentation)) and assume traffic we will not have for years. At 100k DAU a 1% cell is 1,000 users, and most economy questions will be **underpowered**. So: few, large, pre-registered experiments with declared minimum detectable effects — and where randomisation is impossible or too slow, switchback and holdout designs instead of pretending we have power we don't.

**Our differentiator:** the flag system and the **solvency ledger are wired together**. An economy experiment declares its expected issuance cost up front; the platform reserves that cash into the reserve before the flag ramps, and the guardrail that reverts the experiment is the **same coverage-ratio query** that the solvency monitor runs ([`09`](09-points-economy-and-redemption.md) §5). An experiment cannot quietly make us insolvent, because it must be funded before it can run.

## 8. Observability and SLOs — copy **Google SRE**

| Concern                     | What Google SRE says                                                                                                                                                                                                                                                                                   | What we adopt                                                                                                                                                                                   |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **The four golden signals** | **Latency** (split successful vs failed), **traffic**, **errors** (explicit, implicit — a 200 with wrong content — or by policy), **saturation** ([Monitoring Distributed Systems](https://sre.google/sre-book/monitoring-distributed-systems/))                                                       | Every service dashboard is these four, in this order, before anything bespoke                                                                                                                   |
| **What to page on**         | **Symptoms, not causes.** Page only for conditions that are "urgent, actionable, and actively or imminently user-visible"; delete rarely-used alerting rules and unused metrics ([ibid.](https://sre.google/sre-book/monitoring-distributed-systems/))                                                 | A CPU graph never pages anyone. "Users cannot redeem" does                                                                                                                                      |
| **SLO alerting**            | **Multiwindow, multi-burn-rate**: 14.4× over 1h _and_ 5m (2% of budget) → page; 6× over 6h _and_ 30m (5%) → page; 1× over 3d _and_ 6h (10%) → ticket. Both windows must breach, so the alert clears ~5 minutes after the incident does ([SRE Workbook](https://sre.google/workbook/alerting-on-slos/)) | Exactly this table for the four SLOs that matter: **redemption authorize success**, **points-credit latency after a completed watch**, **webhook delivery success**, **store checkout success** |

**What they do badly → our improvement.** The burn-rate maths assumes Google-scale traffic. At [`10`](10-tech-stack.md)'s realistic ~60 rps, a 5-minute window can contain single-digit requests and will flap. Every burn-rate alert gets a **minimum event count** in the short window, or it does not fire.

**Our differentiator:** **economic SLOs sit beside the technical ones.** The coverage ratio, unfunded issuance rate and settlement lag from [`09`](09-points-economy-and-redemption.md) §5 get error budgets and burn-rate alerts of their own. Insolvency is a slow outage; it deserves the same machinery.

## 9. Developer experience for integrators — copy **Stripe and Twilio**

Merchants integrate the Redemption API with a contractor, on a deadline, at a coffee chain's IT budget. DX _is_ the adoption strategy.

| Concern                     | What they do                                                                                                                                                                                                                                                                                                                                                                                                                            | What we adopt                                                                                                                                                               |
| --------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Isolated sandboxes**      | Stripe sandboxes are fully isolated environments; the guidance is **separate sandboxes for local dev and for CI** so automated tests can't corrupt shared state, and you can invite an external implementation partner into one sandbox **without any live-mode access** ([sandboxes](https://docs.stripe.com/sandboxes))                                                                                                               | Per-merchant sandboxes with the same shape, and the ability to add the merchant's agency to the sandbox alone. Nobody's first integration should touch live points          |
| **Deterministic test data** | Stripe publishes magic values that force each branch: `4000000000009995` → `insufficient_funds`, `4000000000000069` → `expired_card`, expiry month 13 → `invalid_expiry_month`, plus dispute and async-refund cards ([testing](https://docs.stripe.com/testing)). Twilio does the same with magic numbers (`+15005550000` → unavailable, `+15005550006` → valid) ([test credentials](https://www.twilio.com/docs/iam/test-credentials)) | A published table of **magic voucher codes** — one per error branch: already-redeemed, expired, wrong-merchant, amount-exceeds-balance, settlement-held, void-after-capture |
| **Local webhook loop**      | `stripe listen --forward-to localhost:4242/webhook` prints a signing secret and forwards live-shaped events; `stripe trigger <event>` fires a fixture ([webhooks](https://docs.stripe.com/webhooks))                                                                                                                                                                                                                                    | A `yourtal` CLI with `listen --forward-to` and `trigger voucher.redeemed`. This single tool removes the worst day of any webhook integration                                |

**What they do badly → our improvement.** Twilio's test credentials **cover only four resource types, return 403 elsewhere, and never fire status callbacks** ([test credentials](https://www.twilio.com/docs/iam/test-credentials)) — so the one thing you most need to test, your callback handler, is exactly what the sandbox cannot exercise. Our sandbox sends **real, signed webhooks** for every event type. And magic values are documented _next to the endpoint that consumes them_, not on a separate page a developer has to know exists.

**Our differentiator:** **go-live is certified, not requested.** A merchant key is promoted to live only after the sandbox has observed their integration handle authorize, capture, void, refund, a duplicate idempotency key, and an expired voucher. It protects the merchant from their own contractor, and it protects our users from a checkout that strands a voucher.

## 10. The short list

If only six things from this doc get built, build these — they are the ones that are cheap now and structurally expensive later.

| #   | Steal                                                                                                  | From                         | Because                                                                                                            |
| --- | ------------------------------------------------------------------------------------------------------ | ---------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| 1   | **`Idempotency-Key` on every value-moving POST**, with the request hash stored and mismatches rejected | Stripe, Amazon, Airbnb       | Retrofitting idempotency into a live ledger means reconciling a period you can never fully reconstruct             |
| 2   | **Append-only double-entry that must balance to zero**, balances as a rebuilt projection               | Square, Uber                 | It makes the solvency invariant in [`09`](09-points-economy-and-redemption.md) §5 a query instead of a spreadsheet |
| 3   | **Integer minor units, one `Money` type, no floats** — and IDR stored in sen                           | Stripe, ISO 4217             | The cheapest bug class in the platform to eliminate, and the most embarrassing to discover late                    |
| 4   | **Dated, pinned API versions + cursor pagination + signed webhooks with poll parity**                  | Stripe                       | The merchant API is a public contract; the first breaking change teaches you whether you designed one              |
| 5   | **Guardrails with auto-revert on every economy flag**, plus a 1% universal holdout                     | Microsoft ExP, Uber, Booking | An unguarded points experiment is an unbounded cash withdrawal                                                     |
| 6   | **Escrow, never destroy, on suspicion** — with reason codes, a countdown and auto-release              | Meta, Google, Cloudflare     | Meta's own number — up to 2 in 10 enforcement actions possibly mistaken — is what our users would have to absorb   |

**And the one thing not to copy:** their scale architecture. Every pattern above is shaped by traffic a thousand times ours. Take the _invariant_ — balance to zero, idempotent by key, symptom-based alerting, gate before publish — and implement it in the smallest thing that holds it, per [`10`](10-tech-stack.md) §1.
