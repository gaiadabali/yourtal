# YourTal — Sending deductions from SnapApp to Free Tax Returns directly

**Date:** 2026-11-04 · **Status:** Proposed, for the lead's review. Designed for group task 4.8.a. The founder's question is in §14; until it is answered, the build uses the recommended option.
**Builds on:** [`26`](26-sign-in-with-yourtal.md) §1.2 (pairwise subs, "YourTal brokers it"), §1.5, §1.9, §2.3 and §3.3 (the teen invite, whose shape this copies); [`29`](29-deletion-across-apps.md) §4.3 (how apps verify YourTal); group 4.1–4.7 (bundle v1 and FTR's pending import); F108, F110, F124.
**Feeds:** group 4.8.a and 4.9.

A person taps "Send to Free Tax Returns" in SnapApp. YourTal asks them to confirm, then gives SnapApp a short-lived assertion that only FTR can open: it names FTR's own `sub` for that person and the SHA-256 of the exact bundle. SnapApp posts the bundle with it to FTR, which checks it with the keys it already uses for YourTal's events and parks the bundle as a pending import on that account, for the person to review (4.6). No file passes through the person's hands, and neither app learns the other's `sub`.

## 1. Decisions

| Question                                                 | Answer                                                                                                                                                                                                                                                                                                                                                                                  |
| -------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| How FTR knows it is the same account                     | Only YourTal can map one app's `sub` to another's, so YourTal says so, with the person present. SnapApp's server opens a **transfer** at YourTal for its own `sub`; the person confirms it on YourTal's screen; YourTal then issues a **transfer assertion** (§4): a JWT signed with its OIDC key, whose `sub` is FTR's pairwise `sub`, bound to the bundle's hash and encrypted to FTR |
| Why not RFC 8693 token exchange, as docs/26 §1.2 planned | oidc-provider 9.12.2 has no token-exchange grant; adding one through `registerGrantType` is hand-written protocol (docs/26 §1.1), and SnapApp keeps no YourTal token to exchange (§1.10). The transfer gives the same guarantees in the teen invite's shape, which is built and reviewed: a client-credentials call, an authorization parameter, a YourTal screen                       |
| Why not FTR pulls from SnapApp                           | FTR would need a SnapApp API, a credential for it and its own way to tie the pull to a SnapApp account: three new parts where this needs one endpoint                                                                                                                                                                                                                                   |
| Why not YourTal carries the bundle                       | YourTal would hold tax data it has no use for. It sees the year, the line count and the hash, never an amount                                                                                                                                                                                                                                                                           |
| Why encrypt as well as sign                              | Signed only, the JWT would show FTR's `sub` to SnapApp, which docs/26 §1.3 forbids ("never share it"). `dir` + A256GCM with a key derived from FTR's client secret (OIDC Core §10.2, as for encrypted ID tokens) costs a few lines on each side. The signature stays: only YourTal's key can make an assertion (docs/29 §1 rejected shared-secret signing for the same reason)          |
| Consent                                                  | Every send, on YourTal's screen, as the signed-in account. No standing permission: the link always goes through YourTal with the person signed in (docs/26 §1.2)                                                                                                                                                                                                                        |
| Where it lands                                           | FTR's pending import (4.5–4.7): one per user and year, replacing an older pending one, accepted or skipped line by line, never overwriting typed values                                                                                                                                                                                                                                 |
| Who may send                                             | An adult in AU, signed in to SnapApp with YourTal, **owner** of the personal workspace, who has signed in to FTR with YourTal and not removed it                                                                                                                                                                                                                                        |
| Switches                                                 | One per app, each run by its operator: YourTal's transfer route (dev and staging only), SnapApp's `FTR_TRANSFER_URL`, FTR's `DEDUCTION_TRANSFER_ENABLED`. Any one off stops it                                                                                                                                                                                                          |

Defaults taken (no founder input needed): **D1** the file stays, as "Save as a file instead": it works for accounts not on YourTal and while any switch is off. **D2** owner only, not admin: totals cover the whole workspace (`deductions.repo.ts:23-35`), so an admin's send would put the owner's deductions in the admin's return. **D3** YourTal keeps a transfer as an `oidc.model` row (kind `AppTransfer`, 15 minutes), so expiry, the purge and `forget_subject` cover it with no migration. **D4** SnapApp gets `send_refused` whatever the reason: YourTal tells the person why, and SnapApp does not learn whether they use FTR. **D5** FTR records the assertion's `jti` in `yourtal_events_seen` (no migration); a repeat gets the first answer, so SnapApp may retry. **D6** FTR accepts a send only while its YourTal sign-in is on, so the person can sign in to review it.

## 3. The flow

1. **SnapApp** `POST /v1/ftr-sends`: builds the bundle, stores its bytes, opens a transfer at YourTal (`fromSub`, year, hash, line count) and starts a YourTal authorization with `transfer=<id>`.
2. **YourTal** `/connect`: signs the person in if needed, checks the transfer (§5) and shows the send screen. **Send** approves it and returns a code to SnapApp; **Cancel** returns `access_denied`.
3. **SnapApp** `POST /v1/ftr-sends/finish`: takes the flow once, redeems the code, checks that the ID token's `sub` is the session's, fetches the assertion, posts the bundle to FTR, records the answer and drops the bytes.
4. **FTR** `POST /api/yourtal/transfers`: opens and verifies the assertion, checks the hash, the `jti` and the account, and parks the bundle as a pending import. SnapApp shows "Sent" with a link to FTR's `/account/import`, where the person signs in and reviews it.

## 4. The assertion

```json
{ "typ": "transfer+jwt", "alg": "RS256", "kid": "2026-10-a" }
{
  "iss": "https://yourtal.gaiada.com/oidc", "aud": "ftr-web", "azp": "snapapp-staging-server",
  "sub": "<FTR's pairwise sub>", "jti": "<the transfer id>", "iat": 1792800300, "exp": 1792800900,
  "region": "AU", "age_band": "adult",
  "kind": "deduction-bundle-v1", "source": "snapapp", "financial_year": "2025-26", "bundle_sha256": "9f2c…"
}
```

- Signed RS256 with the provider's signing key (the JWKS file's first key), then encrypted: a compact JWE with `{"alg":"dir","enc":"A256GCM","cty":"JWT"}` and, as key, the SHA-256 of FTR's client secret. `jti` is the transfer id, `iat` the approval, `exp` the transfer's end (15 minutes after it opened).
- FTR opens it with `dir`/A256GCM only (a bare JWS is refused), then jose `jwtVerify`: RS256; `typ` `transfer+jwt`, so neither an ID token nor a SET passes, nor this as either; the exact `iss`; `aud` its client id; `exp`, `iat`, `jti` and `sub` required; `exp − iat` at most 15 minutes. Then: `region` AU, `age_band` adult, `kind` and `source` as shown; the SHA-256 of the body exactly as received equals `bundle_sha256`; the bundle validates (4.1) and has the same `financialYear`, one FTR supports; the `sub` is linked and not erased.

| FTR answers                                                                                                                                                            | SnapApp                                                         |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| `201 {importId}`, or `200` with the same id for a `jti` already used                                                                                                   | Sent                                                            |
| `400 {err}` `invalid_token`, `bundle_mismatch`, `invalid_bundle`; `409` `no_account`, `conflict`; `413`; `422` `unsupported_year`, `not_allowed`; `404` (switched off) | Not sent; offers the file                                       |
| `429`, `503`, a timeout                                                                                                                                                | One retry with the same assertion while it lasts, then not sent |

## 5. YourTal design (Y1–Y3)

- **Route and scope.** `TRANSFER_ROUTES` beside the clients in `clients.ts`: `{kind: "deduction-bundle-v1", fromSector: "snapapp-staging", toClientId: "ftr-web", regions: ["AU"], environments: ["dev", "staging"]}`; its test checks that the destination is a sign-in client. `snapapp-staging-server` gains the scope `app_transfers`; the guard takes its scope as a parameter.
- **Store** (`transfers.ts`): the adapter's `AppTransfer` rows, `{accountId, fromSector, toClientId, financialYear, bundleSha256, lineCount, approvedAt?}`, for 15 minutes.
- **API** (`transfers.controller.ts`, contracts `oidc/transfer.ts`), each 60 a minute per address:
  - `POST /api/oidc-clients/transfers` `{fromSub, to: "ftr", financialYear, bundleSha256, lineCount}` → `201 {transferId, expiresAt}`; `404 unknown_subject` when `fromSub` is no one in the caller's sector. It never says whether the person uses FTR.
  - `POST /api/oidc-clients/transfers/{id}/assertion` `{fromSub}` → `200 {assertion, expiresAt}`, `no-store`, never kept by the idempotency layer or logged; `409 not_approved`; `409 not_allowed` when a screen check below now fails; `404` for an unknown, expired or other sector's transfer, or a `fromSub` that is not its person.
- **Signer** (`transfer-assertion.ts`): jose `SignJWT`, then `CompactEncrypt` with the destination client's secret as the provider holds it (`provider.Client.find`). jose 6.2.12 joins `apps/api`.
- **Authorization.** `transfer` (a uuid) joins `extraParams`, and is refused together with `teen_invite` or `prompt=create`.
- **`/connect`.** With `transfer` and a covering consent, the screen is `send` instead of `continue` once these pass, else `refused` with `send_refused` and a `sendProblem`: the transfer is live and from this client's sector (`expired`); its person is the signed-in account (`wrong_account`); the account is adult and in the route's regions (`not_allowed`); the destination's consent stands and its `sub` exists (`not_connected`). The send tap runs them again, sets `approvedAt`, logs `send_approved` in the sign-in log, saves the grant and finishes as `continue` does. Without a covering consent the usual consent screen shows; the send then gets `not_approved`, and the person sends again.
- **Copy** (en-AU; id-ID alongside):

> **Send your {year} deductions to Free Tax Returns?**
> Signed in as {name} · {email} · Not you? Use another account
> SnapApp will send Free Tax Returns {lines} deduction lines for {year}: the amount of each, your occupation, your work kilometres and a fingerprint of each receipt. Not the receipts themselves or the shops' names. YourTal only tells Free Tax Returns which of its accounts is yours.
> It arrives as an import for you to check. Nothing in your return changes until you accept it.
> Free Tax Returns is run by {operator}, not by YourTal. [Privacy policy] · [Send] [Cancel]

Refusals, each ending "Nothing was sent.": `not_connected` "Sign in to Free Tax Returns with YourTal once, then send again from SnapApp."; `wrong_account` "This was started from another YourTal account. Switch back to the one you use in SnapApp."; `expired` "This has expired. Start again from SnapApp."; `not_allowed` "Free Tax Returns is for adults in Australia."

## 8. Security

- **Same account.** FTR acts only on a `sub` that YourTal signed for FTR. YourTal signs only for the account that confirmed on its screen, which must own SnapApp's `sub` (checked at the screen and again at the mint) and must be the `sub` in SnapApp's ID token after the code is redeemed.
- **Consent and choice.** Every send needs the person's tap on YourTal's screen, which names the app, its operator, the year and the account; Cancel sends nothing. At FTR it is an import the person accepts line by line or discards. The file stays.
- **Replay.** A single-use flow with PKCE at SnapApp. The assertion lasts at most 15 minutes and is bound to FTR (`aud`), one account (`sub`) and the exact bytes (hash); FTR takes each `jti` once and answers a repeat with the same import.
- **Teens refused** three times: SnapApp offers nothing in a teen space; YourTal requires an adult at the screen and at the mint; FTR requires `age_band` adult. A teen also has no FTR access (`clients.ts:81`).
- **AU only** three times: `country` AU in SnapApp, the route's regions at YourTal, `region` AU at FTR.
- **No join key.** SnapApp carries ciphertext; FTR never sees SnapApp's `sub`; YourTal never sees an amount.
- **A compromised SnapApp** can send only what a person approved, into that person's own FTR account, where it waits for review. **A leaked FTR client secret** opens assertions in transit but cannot make one.

## 10. Risks

- The encryption key is FTR's client secret: rotating it fails sends in flight (minutes; the person sends again). If FTR moves to `private_key_jwt`, encrypt to an FTR key (RSA-OAEP-256) instead.
- F124: staging sends land on FTR's production site. Only accounts linked during a switch-on window can match, as for deletion (docs/29 §10).
- YourTal down: no direct send, and the file still works.
- A personal workspace with a second owner (STATUS: occupation is per workspace) still sends the whole workspace to whichever owner sends. Owner only narrows it; the per-person ruling would close it.
- A send replaces a pending import being reviewed in another tab, as an upload does today (4.6.e's outbox drops it).
- The bundle sits in SnapApp's database up to an hour after an abandoned send: SnapApp's own data, in an RLS table.
- A transfer lives in the provider's table: a change to its purge or to `forget_subject`'s match changes transfers too (Y1 tests both).
- Nothing reaches production while Helios's deploy poller skips YourTal and FTR (STATUS).
