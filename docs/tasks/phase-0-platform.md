### YT-0590 · Line-ending drift recurs, and the only remedy is manual
`todo` · P0 · infra · 1d · dep: YT-0568

- ⚠️ **Filed 2026-09-21 by `yourtal-22` while verifying YT-0568. This is NOT a failure of YT-0568** — that ticket's guard, `scripts/check-line-endings.mjs`, is exactly what caught this, and its fix was correct when applied. What YT-0568 did not establish is that the fix *stays* applied
- ℹ️ **The drift is working-tree-only, which is why nothing else sees it.** The index and every committed blob are LF — measured, not assumed: `git cat-file blob HEAD:.env.example` returns **0** CR bytes while the file on disk had 104 CRLF lines. So `git status` stays clean, `git diff` shows nothing, and `git add --renormalize` stages zero files, because git compares content *after* normalisation and the index is already right. **Every ordinary signal reads green.** `check-line-endings.mjs` is the only detector in the repo
- ⚠️ **It cost this session the first gate of `pnpm verify` and roughly an hour.** Seven files had drifted; until they were repaired, typecheck, lint, test and policy never ran at all, so **no ticket resting on "the tests pass" could be verified.** A red gate does not merely block merging — it suspends the review queue
- ⛔ **The documented remedy is dangerous in this checkout and must be rewritten before it is followed again.** YT-0568 says *delete the affected files and `git checkout -- .`*. Five sessions share this working tree: `git checkout -- .` discards **every** uncommitted change in it, and at the moment this was run that would have destroyed twelve in-flight board files plus another session's `.claude/agents/**` edits. The safe form is `git checkout --` against **the exact paths the guard named**, after confirming each is clean
- [ ] A drifted working tree is repaired by a command a session can run without reading the blast radius first — or the drift is prevented and cannot recur
- [ ] The repair refuses to touch any path carrying uncommitted work, rather than relying on the operator to check
- [ ] **Sabotage-proved in both directions**, per rule 8's precedent: CRLF written into a tracked file is repaired, and a second file holding uncommitted work is provably untouched by the same run
- [ ] The remedy recorded in YT-0568 is corrected, so the next reader does not run `git checkout -- .` in a shared tree
- ✅ **The remedy is corrected at the point of use, which was the more dangerous copy.** `scripts/check-line-endings.mjs` printed *"delete the listed files and `git checkout -- .`"* **at the exact moment a reader is about to act on it** — worse than the prose copy, because nobody reads `_schema.md` while a gate is red. It now prints the paths-only form, tells the reader to check `git status --short -- <paths>` first, and says plainly that a dirty path is someone else's work. `_schema.md`'s copy was already fixed by `yourtal-a4`. The ticket stays open: **the drift itself is still unprevented**, and the first three criteria are untouched
- ✅ **Root cause found 2026-09-21 16:0x by `yourtal-22`, on the third recurrence — and it is not a rogue process. It is ordinary editing, and the repo's own correctness guarantee is what hides it.**
  - `.gitattributes` says `* text=auto eol=lf`. Git applies that on **staging**, so a file written with CRLF is normalised to LF *in the blob* the moment it is added. **Nothing ever rewrites the working tree.**
  - So any session whose editor or tool emits CRLF on Windows produces: a **correct commit**, a **clean `git status`**, and a **wrong working tree — permanently**, until someone happens to re-checkout that path.
  - Caught in the act. `0eec20b` landed at 16:0x touching four `apps/web` modules; within two minutes all four were CRLF on disk. Their blobs at that very commit carry **0 CR bytes** (`git cat-file blob 0eec20b:<path> | tr -cd '\r' | wc -c` → `0`). The commit was right and the tree was wrong, immediately, with no signal.
  - **This is why it recurs and why a one-off renormalisation cannot close it.** Each occurrence is a different session committing perfectly good content. There is no culprit to fix — the drift is a by-product of the normalisation working exactly as designed.
- ⚠️ **It follows that the three criteria above are aimed slightly wrong, and whoever takes this should re-scope before starting.** "Repair without reading the blast radius" treats this as a cleanup problem. It is a **synchronisation** problem: the tree needs rewriting whenever the blob and the tree disagree, which is after every commit and every merge, not once. Candidate shapes — a `post-commit`/`post-checkout` hook that re-checks-out paths the guard names; making the guard itself repair what it finds; or `.editorconfig` plus tool settings so nothing writes CRLF in the first place. **The last one prevents rather than repairs and is the only one that scales to a sixth session.**
- ℹ️ **Consequence worth stating for the review sweep**: every one of these occurrences made `pnpm verify` red at gate 1 while the repository's committed contents were flawless. **A red gate here is not evidence of a defect in anyone's code**, and three sessions have now spent time treating it as one.
- ⚠️ **Recurred twice within 90 minutes on 2026-09-21, which settles that this is a live process and not one bad afternoon.** First occurrence: 7 files at ~14:25. Second, after repair: **3 more by 15:20** — `apps/api/src/modules/watch/checkpoint/checkpoint.service.test.ts`, `apps/web/app/(app)/layout.tsx`, `apps/web/app/(public)/[locale]/layout.tsx`, all clean in git, all CRLF on disk, all silently. **No commit, no edit by this session and no `git status` entry sits between the repair and the reappearance** — which rules out "someone committed CRLF" and points at a tool writing CRLF into the tree as a side effect of ordinary work. Whatever fix YT-0590 lands has to survive that, so a one-off renormalisation will not close it
