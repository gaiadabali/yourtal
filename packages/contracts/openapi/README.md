# Generated contracts

**YT-0031.** The Zod schemas in `../src` are the single source of truth. Everything in this directory is derived from them and checked in.

```bash
pnpm --filter @yourtal/contracts openapi:update      # regenerate the document
pnpm --filter @yourtal/contracts openapi:go          # regenerate the Go types
pnpm --filter @yourtal/contracts openapi:go:check    # CI: fail if Go is stale
pnpm --filter @yourtal/contracts openapi:go:verify   # CI: go build + go vet it
pnpm --filter @yourtal/contracts test                # CI: fail if the document is stale
```

| Artifact                       | Generated by                                        | Edit it? |
| ------------------------------ | --------------------------------------------------- | -------- |
| `yourtal.openapi.json`         | `src/openapi/build-document.ts`, via the drift test | No       |
| `go/model_*.go`, `go/utils.go` | openapi-generator 7.11.0                            | No       |
| `go/go.mod`                    | **hand-written**                                    | Yes      |

## The one thing to know

**The OpenAPI document is a weaker contract than the Zod schemas, permanently.**

JSON Schema cannot express a `.refine()`. Twelve cross-field rules live in `@yourtal/contracts` — "a quick campaign is 60 seconds or shorter", "what the merchant is paid cannot exceed the face value", "expiringPoints cannot exceed availablePoints" — and **none of them survive into this document, the Go types, or any client generated from either.** `z.toJSONSchema` drops them without a word.

We cannot fix that; JSON Schema has no way to say it. What we do instead:

1. Every schema declares its cross-field rules as prose in `src/openapi/schema-registry.ts`.
2. `build-document.ts` emits them into the component description, so they land in the generated Go as doc comments — where the person writing the Go service will actually see them.
3. `openapi.test.ts` asserts the declared count matches the refinements actually on the schema, so **adding a `.refine()` without documenting it fails CI.**

That turns a silent correctness hole into a reviewed one. It does not close it. **Anything that must enforce a cross-field rule has to run the Zod schema, or re-implement the rule and test it** — and per `docs/13` §4, a value-path re-implementation needs its own tests regardless.

## Why there is no generated TypeScript client

Two reasons, and neither is "we didn't get to it".

**There is nothing to generate a client from.** `paths` is empty. No API surface exists yet — endpoints arrive with `apps/api` (YT-0100 onward) and each will be added to this document as it is built. A client with no operations is an empty class.

**The TypeScript types are already derived from the schemas.** `docs/13b` §3: "Types are derived with `z.infer`, never hand-written alongside." `Campaign`, `Listing` and the rest come straight out of the Zod schemas. Generating a second set would create a weaker duplicate that someone would eventually import by accident.

That is not hypothetical — it was tried. `openapi-generator`'s `typescript-fetch` emits `export interface Listing { [key: string]: any | any; ... }`, an index signature that makes every value assignable and that our own lint rejects outright (`@typescript-eslint/no-explicit-any` is an error). Shipping it would have been worse than shipping nothing.

When a real external TS client is needed — a sister app consuming the API over HTTP, per `docs/02` §8 — generate it then, from a document that has paths, with [`openapi-typescript`](https://openapi-ts.dev) rather than openapi-generator. It emits clean types with no `any`.

In the meantime `openapi.test.ts` checks the document back against the Zod shapes directly, so a field silently dropped on the way out fails CI. That is the property a generated-TS round trip would have bought, without the duplicate types.

## Why openapi-generator and not oapi-codegen

oapi-codegen is the more idiomatic Go tool and it was tried first. It parses with kin-openapi, which implements **OpenAPI 3.0 only**, and fails outright:

```
json: cannot unmarshal number into field Schema.exclusiveMinimum of type bool
```

That is the 3.0/3.1 difference — 3.0 spells `exclusiveMinimum` as a boolean flag, 3.1 (JSON Schema 2020-12, which is what Zod emits) spells it as the number. The alternative was to emit a lossy 3.0 variant of the document just for Go, giving two documents that can disagree while both drift checks pass. A second source of truth to please a tool is the exact thing this ticket exists to prevent, so the tool changed instead.

## Two defects the compile check caught

`openapi:go:verify` exists because **generated code that does not compile looks exactly like generated code that does.** Both of these were invisible in review and would have shipped:

- **Colliding enum constants.** `CampaignStatus` and `VoucherStatus` both have an `active` value, and the generator named both constants `ACTIVE` at package scope. `enumClassPrefix=true` makes them `CAMPAIGNSTATUS_ACTIVE` and `VOUCHERSTATUS_ACTIVE`.
- **A missing `utils.go`.** Every generated struct asserts it implements `MappedNullable`, which is declared in a supporting file that `--global-property models` skips.

And one caught by reading the output, which is why there is now a test for it:

- **Money fields as `int32`.** A bare `{"type": "integer"}` carries no width, and generators default to int32. Our money types allow 10,000,000,000 — about five times what an int32 holds — so `FaceValueIdr int32` would silently truncate a legitimate Rupiah amount (`docs/15`: every amount is an integer in its minor unit; for IDR that unit is 1 Rupiah). `build-document.ts` now marks any integer that exceeds int32 as `format: "int64"`, and `openapi.test.ts` fails if one slips through.

## Adding a schema

1. Write the Zod schema in `../src/<domain>/`.
2. Register it in `../src/openapi/schema-registry.ts`, with its cross-field rules.
3. `pnpm --filter @yourtal/contracts openapi:update`
4. `pnpm --filter @yourtal/contracts openapi:go`
5. Commit the regenerated artifacts with the schema change.

Skip step 2 and the completeness test fails: an unregistered schema never reaches the document, and a Go service silently has no type for it.
